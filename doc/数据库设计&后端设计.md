# 随机生成幸福事件 UniApp 项目数据库设计文档（修订版）

## 一、数据库概述
本项目数据库主要用于存储幸福事件的相关信息，包括预设的幸福事件列表、用户已生成的幸福事件记录等，以支持应用的核心功能，即随机生成幸福事件、查看历史记录和重置事件列表。

## 二、数据库结构设计

### （一）幸福事件表（happiness_events）
用于存储所有预设的幸福事件信息。

| 字段名 | 数据类型 | 是否主键 | 是否必填 | 描述 |
|--------|----------|----------|----------|------|
| event_id | INT | 是 | 是 | 幸福事件的唯一标识 |
| event_desc | VARCHAR(255) | 否 | 是 | 幸福事件的具体描述，如“去听一首音乐” |
| event_image_path | VARCHAR(255) | 否 | 是 | 事件对应的图片资源路径 |

### （二）用户表（users）
用于存储用户信息。

| 字段名 | 数据类型 | 是否主键 | 是否必填 | 描述 |
|--------|----------|----------|----------|------|
| user_id | INT | 是 | 是 | 用户的唯一标识 |
| username | VARCHAR(50) | 否 | 是 | 用户的名称 |

### （三）用户事件记录表（user_event_records）
用于记录用户已生成的幸福事件，以便用户查看历史记录。

| 字段名 | 数据类型 | 是否主键 | 是否必填 | 描述 |
|--------|----------|----------|----------|------|
| record_id | INT | 是 | 是 | 记录的唯一标识 |
| user_id | INT | 否 | 是 | 用户的唯一标识 |
| event_id | INT | 否 | 是 | 对应的幸福事件的ID |
| generate_time | DATETIME | 否 | 是 | 事件生成的时间 |

## 三、数据关系设计
- 用户表（users）与用户事件记录表（user_event_records）之间是一对多的关系，一个用户可以生成多个幸福事件记录。
- 幸福事件表（happiness_events）与用户事件记录表（user_event_records）之间是一对多的关系，一个幸福事件可以被多个用户生成。
- 用户事件记录表（user_event_records）通过 user_id 和 event_id 字段分别与用户表（users）和幸福事件表（happiness_events）建立外键关联，以确保数据的一致性和完整性。

## 四、数据初始化
在应用启动时，检查数据库中的幸福事件表是否为空。如果为空，则插入预设的幸福事件数据，确保应用能够正常运行。预设的幸福事件可以包括以下内容：

# 随机生成幸福事件 UniApp 项目后端设计文档（修订版）

## 一、后端架构概述
本项目后端采用基于Node.js的架构，结合Express框架搭建RESTful API服务器，负责处理客户端的请求，与数据库进行交互，实现业务逻辑。同时，使用UniApp的云开发环境，充分利用其提供的云函数和数据库服务，以简化开发流程并提高应用的性能和可扩展性。

## 二、接口设计

### （一）生成幸福事件接口
- **接口地址**：/api/generateEvent
- **请求方法**：POST
- **功能描述**：用户点击“生成幸福事件”按钮时调用，从该用户尚未使用的幸福事件中随机选择一个事件，返回事件描述和对应的图片路径，并记录该用户已使用该事件。
- **请求参数**：
  - user_id（用户ID，用于记录用户生成的事件）
- **响应参数**：
  - event_id（幸福事件ID）
  - event_desc（幸福事件描述）
  - event_image_path（幸福事件图片路径）
  - status（操作状态，成功或失败）
  - message（提示信息）

### （二）查看历史记录接口
- **接口地址**：/api/getHistory
- **请求方法**：POST
- **功能描述**：用户点击“查看历史记录”按钮时调用，获取该用户已生成的幸福事件列表，按生成时间倒序排列。
- **请求参数**：
  - user_id（用户ID）
- **响应参数**：
  - history_list（历史记录列表，包含event_id、event_desc、generate_time等信息）
  - status（操作状态，成功或失败）
  - message（提示信息）

### （三）重置事件列表接口
- **接口地址**：/api/resetEvents
- **请求方法**：POST
- **功能描述**：用户点击“重置事件列表”按钮并确认后调用，清空该用户已生成的事件记录，使所有幸福事件对该用户重新可用。
- **请求参数**：
  - user_id（用户ID）
- **响应参数**：
  - status（操作状态，成功或失败）
  - message（提示信息）

### （四）获取事件详情接口
- **接口地址**：/api/getEventDetail
- **请求方法**：POST
- **功能描述**：用户在历史记录界面点击事件条目时调用，获取指定幸福事件的详细信息，包括事件描述、生成时间和对应的图片路径。
- **请求参数**：
  - event_id（幸福事件ID）
  - user_id（用户ID，用于验证事件是否属于该用户）
- **响应参数**：
  - event_id（幸福事件ID）
  - event_desc（幸福事件描述）
  - event_image_path（幸福事件图片路径）
  - generate_time（生成时间）
  - status（操作状态，成功或失败）
  - message（提示信息）

## 三、业务逻辑实现

### （一）生成幸福事件逻辑
1. 接收客户端传来的user_id。
2. 查询数据库中的幸福事件表，获取所有幸福事件的event_id和event_desc。
3. 查询用户事件记录表，获取该用户已生成的事件的event_id列表。
4. 从所有幸福事件中筛选出该用户尚未使用的事件。
5. 如果没有可生成的事件（即该用户已使用所有事件），返回提示信息给客户端，询问用户是否重置事件列表。
6. 如果有可生成的事件，随机选择一个事件。
7. 在用户事件记录表中插入新的记录，记录该用户生成了该事件。
8. 将选中的事件的event_id、event_desc和event_image_path返回给客户端。

### （二）查看历史记录逻辑
1. 接收客户端传来的user_id。
2. 查询数据库中的用户事件记录表，获取该用户的所有记录，按generate_time倒序排列。
3. 对于每条记录，查询幸福事件表获取对应的event_desc和event_image_path。
4. 将历史记录列表返回给客户端，包括每个事件的event_id、event_desc、generate_time和event_image_path。

### （三）重置事件列表逻辑
1. 接收客户端传来的user_id。
2. 删除用户事件记录表中该用户的所有记录。
3. 返回重置成功的提示信息给客户端。

### （四）获取事件详情逻辑
1. 接收客户端传来的event_id和user_id。
2. 查询用户事件记录表，验证该event_id是否属于该user_id。
3. 如果验证通过，查询幸福事件表获取该事件的event_desc和event_image_path。
4. 查询用户事件记录表获取该事件的generate_time。
5. 将事件详情返回给客户端。

## 四、异常处理机制

### （一）事件列表为空异常
- 当生成幸福事件接口检测到没有可生成的事件时，返回特定的提示信息给客户端，询问用户是否重置事件列表。客户端收到后，弹出提示框给用户选择。

### （二）图片加载失败异常
- 在返回事件图片路径给客户端时，后端可以同时返回一个默认的占位图片路径。如果客户端发现图片加载失败，可以使用占位图片，并提示用户检查网络连接或重新加载。

### （三）网络异常
- 后端接口在处理请求时，如果检测到网络问题（如数据库连接失败等），返回网络异常的提示信息给客户端。客户端收到后，在启动界面弹出提示框，提示用户检查网络设置，并提供“重试”按钮，用户点击后重新加载应用。

## 五、性能优化策略

### （一）数据库查询优化
- 对幸福事件表和用户事件记录表建立适当的索引，提高查询效率。例如，对用户事件记录表的user_id和generate_time字段建立联合索引。

### （二）缓存机制
- 使用缓存技术（如Redis）缓存经常访问的数据，如幸福事件列表，减少数据库的访问频率，提高响应速度。

### （三）异步处理
- 对于一些耗时的操作，如重置事件列表时的数据库更新，可以采用异步处理的方式，避免阻塞主线程，提高系统的并发处理能力。

## 六、安全性考虑

### （一）数据验证
- 在接口接收客户端传来的数据时，进行严格的验证，确保数据的完整性和合法性。例如，检查user_id是否为有效的整数，event_id是否存在于数据库中等。

### （二）防止SQL注入
- 使用参数化查询或ORM框架，避免直接拼接SQL语句，防止SQL注入攻击。

### （三）HTTPS加密
- 在数据传输过程中，使用HTTPS协议对数据进行加密，确保数据的安全性，防止被窃取或篡改。

## 七、可扩展性设计

### （一）模块化设计
- 将后端代码按照功能模块进行划分，如事件生成模块、历史记录模块、重置模块等，每个模块独立开发和维护，便于后续的功能扩展和代码管理。

### （二）接口设计的灵活性
- 在设计接口时，考虑未来的扩展需求，预留一些可选参数或扩展字段。例如，在生成幸福事件接口中，可以增加一个category参数，用于后续按事件类别进行筛选生成。

### （三）数据库的可扩展性
- 数据库设计应具有良好的规范性，便于后续的数据扩展和表结构调整。同时，可以考虑使用分布式数据库或云数据库，以应对用户量和数据量的增长。
